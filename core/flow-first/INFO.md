## Какую проблему решает

Агент получил задачу и сразу пошёл писать код. Через 10 файлов оказалось, что он начал не с того слоя — UI меняет когда задача про БД, или меняет email-сервис когда речь про SMTP-настройки. Контекст разбух, время потрачено, результат не тот.

Без сверки понимания на старте — `library-first` строится на догадках: ищет готовое не для того слоя, оценка LOC втрое мимо, найденное решение не подходит по контексту.

## Как работает

Пользователь даёт 2-3 зацепки — файл, таблица, роут, сервис. Скилл читает **только их** (не сканирует весь проект), на основе чтения заполняет таблицу 4×3: Ландшафт / Проблема / Решение / Результат × UI / БД / Интеграции.

Каждая ячейка либо заполнена конкретным фактом из кода, либо явно помечена «не затронут». Молчание о слое запрещено. Если ячейка не заполнима — один точечный вопрос пользователю, не пять.

Таблица показывается одним сообщением, одновременно записывается в `tasks/log/`. Ждёт явный «ок» — без апрува дальше ничего не происходит.

## Результат работы

Library-first строится на понимании, не на догадках. LOC-оценка точная, готовое решение находится по тому слою где задача. На фронте начала работы — таблица 4×3 как чек-лист понимания, на которую можно вернуться через час и помнить контекст.

В долгом проекте — 5-10 минут на flow-first экономят 1-3 часа на «не туда полез».

## С какими скиллами работает

| Скилл | Зачем |
|---|---|
| idea-first | Определяет тип задачи (продукт/фича/фикс) — flow-first стартует с этим знанием |
| library-first | После апрува таблицы — анализ что готово, что с нуля |
| arch-map | Привязка артефакта к слою архитектуры |
