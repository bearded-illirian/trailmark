## Какую проблему решает

Каждая задача затрагивает один или несколько слоёв архитектуры — но в конце никто не знает, какие именно. Через месяц при поиске «что было сделано в слое X» — никаких меток, никакой связи между задачами и архитектурой.

Без автоматической привязки — каждый артефакт «висит в воздухе»: бриф, ТЗ, эпик, задача не знают к какой части архитектуры относятся. Невозможно собрать roadmap по слою, нельзя проследить эволюцию модуля.

## Как работает

Скилл читает `arch_items` из `platform.sqlite` — реестр элементов архитектуры (модули, сервисы, API, БД-таблицы). Работает в двух режимах. **File-mode** — после `plan-first` сверяет пути изменённых файлов с путями архитектурных элементов. **Feature-mode** — после `brief` или `tz` ищет в тексте артефакта slug/title/url элементов.

Merge-логика: не перезаписывает существующий `arch_ref`, а дополняет (если артефакт затрагивает несколько слоёв). При закрытии задачи через ship-first — propagate финального arch_ref вверх по цепочке `epic → tz → brief`.

Полностью автоматический. Не спрашивает пользователя, не блокирует задачу. Если `arch_items` пуст или элементы не найдены — просто `arch_ref = null` без ошибки.

## Результат работы

Каждая задача / эпик / ТЗ / бриф имеют явные ссылки на слои архитектуры. Можно собрать список «все задачи которые касались модуля X» одним SQL-запросом. Roadmap по слою строится автоматически.

Через месяц приходишь — видишь, что слой `api/billing` за последние 30 дней получил 4 задачи: список + ссылки + контекст. Архитектура — живой инструмент, а не схема в отдельном файле.
