## Какую проблему решает

Большая задача (5+ блоков, миграция БД, переписывание скиллов) запускается как обычный `/go-fast` — и через два дня превращается в кашу: блоки пересекаются, решения принимаются втихую, scope расползается, follow-up эпики неуловимо рождаются прямо внутри задачи.

Без явного протокола архитектурной чистоты — каждый сложный блок «решается на ходу», без фиксации почему сделано так, а не иначе. Через месяц никто не помнит, что в каком блоке решали.

## Как работает

Декомпозиция задачи в пронумерованные блоки с явной целью каждого. Внутри каждого блока — полный цикл `flow-first → library-first → plan-first → execute → ship-first`. Между блоками — фиксация архитектурных решений и scope vs out-of-scope.

Если у задачи есть незнакомый компонент — отдельная **research-фаза до планирования**, выдающая сравнительную таблицу «как сейчас vs как должно быть» с критичностью пунктов.

После каждого блока — отчёт с явной фиксацией: какие решения приняты, что в out-of-scope, что в follow-up. Эпики выносятся явно, не рождаются втихую.

## Результат работы

Сложная задача не разваливается. Через месяц в каждом блоке понятно: что решено, почему, что осталось в out-of-scope, что вынесено в follow-up эпик. Архитектурные решения зафиксированы явно, а не «в комментариях кода».

Если задача в моменте оказалась слишком большой — она структурно делится на новые задачи / эпик, не превращаясь в скрытый эпик внутри одного `task.md`.
